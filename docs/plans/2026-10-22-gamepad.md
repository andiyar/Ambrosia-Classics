## Brainstorm (short)

- **Where the pad meets the game.** Every game polls `ShellView.pollKeyState()` (GetKeys) and gets menu key-downs as
  events. So a pad must (a) add held keys to the polled state and (b) produce key-down / key-up edges the app can feed to
  the same path a keyboard key-down takes. Cores never see a pad (D6).
- **Translation is pure.** Button state → key codes is a Foundation-only translator (edges, hold delays, a Caps Lock
  latch) — unit-testable, and shareable with the Windows/SDL build, which does not link HectorShell (AppKit). So it goes
  in a new Foundation-only kit target **`HectorInput`**, which HectorShell depends on and re-exports. The GameController
  reader sits in HectorShell (Apple framework, app-shell side).
- **BTX specifics** (bank `front-end.md` §3g/§4, `Prefs/KeySet.swift`): play reads the current key set's five keys
  (left, right, up, down, push); **pause is Caps Lock's lock state** (not a held key) — a pad needs a latch; Esc ends a
  game at once unless the "Hold Escape to exit" pref (default off); the menu starts a game on N / Return / Enter; demos
  end on any key; screens return on any key; dialogs take Return / Esc. The original's InputSprocket support (bool 0x41)
  was a stub on OS X — so a pad has precedent in the original's own intent, but nothing in 1.1 to replicate.
- **Kid-friendly layout:** every face button pushes (no "which one is A" problem — Nintendo and Xbox swap labels);
  d-pad and left stick both move; + / Menu / Options pauses and un-pauses; − / View / Share must be held 1 s to end a
  game (a stray press does nothing); on menus / screens / dialogs any face button or + is Return (start, continue, OK).
- **Remap follows:** the layout is built from BTX's current key set on every poll, so remapping a key in Preferences
  remaps the button.

## Tasks

### K1 — HectorKit: `HectorInput` + the GameController reader + `ShellView` merge (⚑ MAJOR: new public API)

Repo: HectorKit worktree. Contracts:

1. **`HectorInput`** target + library product, Foundation-only, no dependencies. `HectorShell` depends on it and
   `@_exported import`s it (adopters write `import HectorShell` only).
   - `ShellPadButton` (Hashable, Sendable, CaseIterable): `up down left right` (d-pad; the left stick folds in),
     positional face buttons `south east west north`, `leftShoulder rightShoulder leftTrigger rightTrigger`,
     `start` (+ / Menu / Options), `back` (− / View / Share-less "select"), `leftThumb rightThumb`.
   - `ShellPadState` (Sendable, Equatable): `buttons: Set<ShellPadButton>`; `static func stickDirections(x:y:) ->
     Set<ShellPadButton>` — axes in −1…1, y up positive; a direction is held when its axis is beyond **0.5** (diagonals
     allowed: both axes may hold); `.empty`.
   - `ShellPadBinding` (Sendable, Equatable): `.key(UInt16)` (held while the button is), `.keyAfterHold(UInt16,
     seconds: Double)` (held only once the button has been down that long, continuously), `.capsLockToggle`.
   - `ShellPadMapping` (Sendable, Equatable): `bindings: [ShellPadButton: ShellPadBinding]` (one per button; several
     buttons may name the same key).
   - `ShellPadTranslator` (Sendable struct): `mutating func update(_ state: ShellPadState, mapping: ShellPadMapping,
     now: TimeInterval) -> ShellPadFrame`; `mutating func reset()`.
     `ShellPadFrame`: `held: Set<UInt16>`, `pressed: [UInt16]`, `released: [UInt16]` (both ascending), `capsLock: Bool`.
     Rules: `held` = keys of the bindings whose button is down (and, for a hold binding, has been down ≥ `seconds`);
     edges are by KEY CODE against the previous update's `held` (two buttons on one key: one down edge, one up edge);
     the latch flips on each down-edge of a `.capsLockToggle` button and is **cleared whenever the mapping has no
     `.capsLockToggle`**; a mapping change mid-hold re-derives `held` and yields the edges of the difference; `reset()`
     forgets everything with no edges.
2. **HectorShell (`#if canImport(GameController)`)**: `@MainActor protocol ShellPadSource { func padState() ->
   ShellPadState }`; `ShellGamepad: ShellPadSource` = the union of every connected `GCController`: extended gamepad
   (d-pad, left stick folded, A→south B→east X→west Y→north, shoulders, triggers pressed, menu→start,
   options→back, thumbstick buttons) else micro gamepad (d-pad, A→south, X→west, menu→start). No discovery calls, no
   background monitoring, no Info.plist keys required.
3. **`ShellView` (macOS)**: `public var padMapping: ShellPadMapping?` (default nil = pad off; Aki / Deimos / Ferazel
   unchanged). Internal test seam `padSource: ShellPadSource?` (a `ShellGamepad` is made on first non-nil mapping).
   `pollKeyState()` with a mapping: reads the pad (empty while the app is inactive), runs the translator with the
   monotonic clock, delivers edges to the handler (**releases first, then presses**, ascending) through two new
   `ShellInputHandler` methods `shellView(_:padKeyDown:)` / `shellView(_:padKeyUp:)` (default no-ops), then returns
   the keyboard state merged: `held` ∪ pad `held`, `capsLock` ‖ latch. `keyState` stays keyboard-only. A
   `pollKeyState()` re-entered from a pad callback does not re-read the pad (returns keyboard ∪ the frame in hand).
   Setting `padMapping` to nil resets the translator. `public private(set) var padFrame: ShellPadFrame` for
   diagnostics.
4. **Tests**: translator rules (each bullet above), stick folding + threshold, ShellView merge + edge order + inactive
   app + nil mapping + re-entry with a fake source. The zero-skip floor rises from **328** to the new executed total
   (`tools/check-zero-skip.sh`, FLOOR bumped in the same commit). HK `docs/DECISIONS.md` **D16**; README module list.
   Done: `swift test` green, gate PASS at the new floor, committed on `gamepad`.

   same file): `static func mapping(keySet: KeySet, inGame: Bool) -> ShellPadMapping`.
   In a game (play, not demo): up/down/left/right → the set's four keys; south/east/west/north → push;
   start → `.capsLockToggle`; back → `.keyAfterHold(0x35 Esc, seconds: 1)`. Otherwise (menu, screens, demo, dialogs):

## Review record (Fable cross-check, 2026-10-22) — folded into the contracts below, which WIN over the text above

1. **[Critical] Dialogs.** Every BTX dialog (DLOG 1000 name entry, prefs 190, level select, alerts) is a `CarbonDialog`
   on `BTXDialogs.stack`; `selectClock()` stops every game clock while `dialogs.isModal`, so nothing polls. A1: the
   dialogs' existing 1/60 `nullTimer` (BTXDialogs.swift `startRouting`) also calls a controller hook that polls
   `shell.view.pollKeyState()`. The dialog keys live in a LOCAL EVENT MONITOR (`consumes` → `handleKeyDown`), so a pad
   Return / Esc reaches a dialog as a synthesized key-down (+ key-up) posted with `NSApp.postEvent(_:atStart:)` carrying
   the front panel's `windowNumber` — never `window.sendEvent` (bypasses the monitor).
2. **[Critical] D-pad outside play.** The menu switches on `chars` (L level select, Q quit, X/Z poem/quote, W/B
   sounds…), so "d-pad → the set's keys" outside play would fire commands with the J/L/I/K, Z/X, QWER sets. Outside
   play the d-pad is the fixed arrows 0x7B–0x7E (the menu ignores them).
3. While a play session `isInGame`, `start` stays `.capsLockToggle` even with a dialog up (so the latch — the pause —
   survives a dialog); the face buttons and `back` are Return / Esc whenever `dialogs.isModal`.
4. `ShellView.padMapping` assigned every poll: setting an EQUAL mapping is a no-op (hold timers must not restart); a
   changed non-nil mapping re-derives (K1.1); nil resets.
5. `ShellKeyCharacters` (US unmodified `NSEvent.characters` per Carbon key code: letters, digits, Space " ", Return
   "\r", Enter "\u{03}", Tab, Delete "\u{7F}", Esc "\u{1B}", arrows as the 0xF700-series private-use scalars, keypad
   digits) lives in **HectorInput**; BTX uses it for pad key-down `chars` (W1 may point `WinKeyNames` at it).
6. Esc is read only in play, not in the pause: "− held 1 s" works only un-paused; with "Hold Escape to exit" on the
   total hold is ≈ 1 s + 31 frames. GAMEPAD.md says so.
7. `@_exported import HectorInput` in a HectorShell file compiled for iOS too (AkiPad builds HectorShell).
8. A real-pad check is owed: no controller is connected to this Mac now (the Pro Controller is paired, not connected),
   so the staged notes carry a 6-line pad checklist for Ben (start from menu with a face button, move, push, + pause /
   unpause, − hold ends, name dialog OK). GameController facts (no Info.plist keys / entitlements for a non-sandboxed
   app; values read on the main thread update without handlers; `shouldMonitorBackgroundEvents` default off) hold.
9. W1: the pad source is injected into `WinGameDriver` (BTXWinKit stays Foundation-only; HectorSDL in the executable);
